# 3 - Text style estimation and re-rendering (Keepframe)

Caveat: pages were read through a summarising fetch tool, not line-by-line. Numbers marked (V) were stated in fetched text; (U) = not verified. I read no Hangul-specific font-ID benchmark; none turned up.

## 1. Recommendations (ranked for this product)

Key finding: nobody reliably names a font from pixels. VLMs are weak (best ~24-31%), classic CNNs need clean horizontal crops and a closed class list, and the reels use mostly clean geometric sans (Inter/Poppins-like UI text) plus a script accent and a serif logo. So do NOT chase the font name. Treat font as **retrieval over a small installed set, verified by render-and-compare against the plate-matted glyph mask**. Colour, weight, size, spacing, shadow and gradient are solved as a fitting problem (analysis-by-synthesis), which is CPU-cheap and testable.

**R1. Render-and-compare font and parameter fit (core, CPU, no model).**
Inputs: crop sequence, local plate crop (known background), OCR string/box.
1. Matte the text: alpha = estimate from |frame - plate| projected on the dominant colour direction (see R2). Take the best-contrast, non-blurred, non-occluded frame (max Laplacian energy inside box; avoid motion-blur frames and reveal-wipe frames).
2. Candidate fonts: ~40-80 faces bundled in the Chromium renderer: Inter, Poppins, DM Sans, Manrope, Plus Jakarta, Montserrat, Space Grotesk, Playfair/DM Serif, one or two scripts (Caveat/Dancing/Pacifico-like, Homemade Apple), mono, and for Hangul Pretendard/Noto Sans KR/Noto Serif KR. Include weights 100-900 (variable fonts give weight as a continuous axis).
3. For each candidate render the OCR string with HTML canvas/Chromium, scale to the matte's cap/x-height, and score IoU/Chamfer distance between the rendered coverage and the matte alpha (after optimising size, letter-spacing, weight, small shear). Pre-filter with cheap shape descriptors (x-height/cap-height ratio, stroke/height ratio, serif presence, aspect per char) so only 5-10 candidates get full fitting.
4. Output: top-3 families with scores; if the best score is below a threshold or two are indistinguishable, keep the best and flag low confidence (the user edit panel offers the top-3).
5. Optional re-ranker: send the crop + top-3 renders to the hosted VLM only to choose among candidates ("which rendering matches?" - side-by-side comparison, not open naming). I could not verify accuracy of this; treat as experimental (see 2.2: VLMs fail at open font naming, but pairwise judging is a different task).
Test: build a synthetic set by rendering known strings in the bundle with random colour/blur/H.264 compression/gradient over plates; measure top-1/top-3 family and weight error (target top-3 >= 90%, weight within one step, size within 3%, letter-spacing within 0.02 em). Then check on 10 hand-labelled real crops from the four references.

**R2. Colour: two-colour/alpha model against the known plate, not the global background.**
Per pixel, frame = a*C + (1-a)*B where B = local plate (known). Solve per text box: for pixels with |frame-plate| large, estimate C as the robust (median) solution of C = B + (F-B)/a with a from a distance-transform/ erosion model (interior pixels at distance > stroke_radius from the edge have a=1 so C = F directly). Practical recipe: threshold |F-B|, erode by ~0.35*stroke width, take the median Lab of the surviving interior pixels = fill colour. Hold-out: reproject (C,a,B) and compare to F (residual map). This removes the "colour on a coloured object" error because B is local. Gradients: fit a linear (two-stop) gradient C(x,y) by least squares over interior pixels; keep it only if residual falls by a clear margin vs. a flat fill (e.g. >40% lower), else flat. Text in a fade: fit per-frame opacity as the scale factor, not a colour change (use the frame with max opacity for colour). Failure modes: glow/shadow pixels get counted as fill (the erosion helps); thin strokes (<3 px) have no interior - use max-contrast percentile instead; the plate is itself wrong where the text sat static for most frames (baked-in text; fix upstream in plate work); semi-transparent glass cards need the card colour as B per frame.

**R3. Weight, size, spacing from measurements, not VLM.** Weight = stroke width / cap height measured by distance-transform ridge (median of 2*max-inscribed-circle radius along the skeleton); map to the font's weight axis by calibrating the chosen font (render it at weights 100-900 and look up the ratio). Letter spacing: compare measured per-glyph centres (from OCR per-char boxes or connected components) to the font's advances, solve one tracking value in em. Graphic-Design-Bench (arXiv 2604.04192, 2026) reports letter spacing is the property VLMs predict most consistently, while size and line-height vary up to 4x across models (V) - another reason to measure geometrically and use a VLM only as a prior.

**R4. Effects (outline, shadow, glow): fit after fill.** Subtract the fitted fill+plate rendering from the frame; the residual outside the glyph mask is the effect. Decide with a small model-selection test: drop shadow = residual offset dark blob, correlation with a shifted/blurred mask (grid search offset, blur sigma, opacity, colour); glow = zero-offset, large sigma, bright colour; outline = thin ring at constant distance. Emit CSS text-shadow/-webkit-text-stroke (both export to AE layer styles). Accept an effect only if residual energy drops materially. Test via synthetic renders with known shadow parameters.

**R5. Hosted/GPU re-rendering of new text in the original style = optional "pretty" path, not default.** For edit-after (user changes the string), the default should be HTML text rendered with the fitted font/colour/effects, because it stays editable and exports to AE. Neural scene-text editors (below) are only needed for photographic/handwritten/3D-lit text where a font fit fails, and the models are GPU-bound.

## 2. Hangul/CJK fallback while keeping the look
No paper gives a ready Latin-to-Hangul font-matching method for typography; I found one related system (LoGAN, 2.5). Practical method:
1. Classify the Latin font into attribute buckets: category (geometric/humanist/grotesque sans, serif, slab, script, mono, rounded), weight (stroke ratio), width, contrast, x-height. These come free from R1 (the matched family's metadata, or the fitted weight).
2. Fixed map bucket -> Korean family, each with matched weights: geometric/neo-grotesque sans -> Pretendard (Inter-derived Latin; best Latin-Hangul pairing, covers 9 weights) or Noto Sans KR; humanist/rounded -> Noto Sans KR/ Gowun Dodum / Nanum Square Round; serif -> Noto Serif KR / Nanum Myeongjo / Gowun Batang; script/display -> no real Hangul script exists; fall back to Nanum Pen/Gaegu/Hi Melody only if a handwriting look is detected, else sans at matching weight with slight shear. Mono -> D2Coding.
3. Match weight by stroke/cap-height ratio calibrated on the Hangul face (Hangul stroke density is higher; do not copy numeric weight 1:1 - re-fit weight on a reference Hangul string rendered at same height). Match size by x-height-equivalent: scale Hangul so its ideographic em-box visually matches Latin cap height (Hangul usually needs ~0.9-0.95 of the Latin size to look equal).
4. Keep colour/effects/gradient/tracking unchanged; set tracking slightly negative for Hangul (-0.01 to -0.03 em) since syllable blocks are wide.
5. Test: render the same sentence in the original and in the fallback; compare visual weight (mean alpha over bbox) and bbox height with a tolerance; human A/B on 10 clips.

## 3. Per-paper notes

**2.1 DeepFont, Wang et al. 2015 (ACM MM; arXiv 1507.03196).** AdobeVFR: 2.38M synthetic images across 2,383 classes; 197,396 unlabelled real; 4,384 labelled real test across 617 classes (V). Top-1 ~71%, top-5 >80% on real test (V). Stacked conv auto-encoder for synthetic-to-real domain adaptation; augmentation of char spacing and aspect ratio; 6x model compression (V). Limits (V): heavily edited text (spacing/distortion), 3D effects, foreground obstacles, complex backgrounds - i.e. exactly motion-graphics. Closed to Adobe's 2,383 commercial fonts; dataset/model licensing unclear (U), original release was limited.

**2.2 "Texture or Semantics? VLMs Get Lost in Font Recognition", 2025 (arXiv 2503.23768).** 13 VLMs on FRB (15 fonts; easy and hard "stroop" versions). Best easy ~31% (Claude-3.5-Sonnet), GPT-4o-mini 0%, open models mostly <10%, hard mostly <15% (V). CoT negligible; few-shot gains <4 points; attention misses character edges (V). Implication: do not ask a VLM to name a font. Authors' benchmark is 15 fonts only.

**2.3 Graphic-Design-Bench, 2026 (arXiv 2604.04192).** 2,568 text elements, 167 typefaces; best top-1 font ID 23.7%; colour best deltaE 5.57 with 63.3% acceptable, weak models deltaE>52 (V). Use as the realistic ceiling for a hosted VLM: usable as a prior for colour (deltaE ~5), not for font. I did not read tables beyond the first 100k characters.

**2.4 LoGAN: Multilingual Font Localization with Generative Agents, 2026 (arXiv 2609.07029).** Three stages: design extraction (VLM agent: GPT-5.2 or Qwen3-VL-32B), transfer (abstract-shape kerning transfer, 4 boundary shapes), generation (2B glyph model, 27 languages incl. CJK/Korean, trained on 15,000 fonts / 40M glyphs). Stage 1 7.6-38.5 s; stages 2-3 25.5-43.2 s on A100 40GB; 97% pipeline success on 1,800 runs (V). Limits: connected/calligraphic fonts, single font only. GPU; licence/code (U). Relevant as the only recent cross-script style-localisation work; too heavy and mostly for stylised display titles. Its kerning-transfer heuristic (shape-class pairs) is a cheap idea to borrow.

**2.5 TextStyleBrush, Krishnan et al. 2021 (Facebook AI; arXiv 2106.08385).** Self-supervised: style/content encoders + StyleGAN2 generator, unsupervised foreground mask, typeface classifier pretrained on synthetic fonts. Introduced Imgur5K handwriting (135K words, ~5,300 writers). Failures (V): inconsistent per-character colours, metallic effects, calligraphy, <3-character sources. Latin only, GPU; no clear open-source licence stated in the text I read (U); training code was not generally released (U). Avoid.

**2.6 MOSTEL (AAAI 2023, "Exploring Stroke-Level Modifications for Scene Text Editing"), DiffSTE (2023), TextCtrl (NeurIPS 2024 spotlight; github weichaozeng/TextCtrl).** GAN/diffusion scene-text editors; TextCtrl uses glyph-adaptive self-attention for style/structure disentanglement, built on SD 1.5, PyTorch 1.13/CUDA 11.6, multiple weights (VGG19, ViTSTR, SD1.5) (V); licence not found (U). Latin-centric; recent papers state Korean/Arabic/Japanese remain poorly handled. Needs GPU; weights ~SD1.5 scale (~1B params). Not CPU-feasible at useful speed (U: no CPU timings published).

**2.7 AnyText (ICLR 2024; arXiv 2311.03054).** ControlNet-style diffusion with glyph-image conditioning rendered in one font ("Arial Unicode"), OCR-based text embedding; 1431.6M params; 3,512 ms/image on V100 batch 4; training set includes ~1.6M Chinese, 1.39M English plus smaller Japanese/Korean, etc. (V). Limits: very small fonts; no explicit font control. The best-supported hosted option for Hangul in-image generation (GPU/HF Space), but it re-generates pixels, not editable vectors.

**2.8 TextDiffuser-2 (2023; arXiv 2311.16465).** Two LLMs (Vicuna-7B layout planner + diffusion with line-level tokens), 922M-parameter diffusion part; 1.1 s layout + 6 s/50-step image on A100; trained on MARIO-10M (V). Complex scripts (Chinese) suffer because new tokens enlarge the vocabulary (V). Text-to-image, not frame-conditioned editing.

**2.9 STELLAR (arXiv 2511.09977, 2025)** low-resource-language scene text editing (Korean, Arabic) with a TAS style metric; the summary I got lacked numbers, architecture and release status (U). Worth a second look only if a neural Hangul editing path is ever needed.
**2.10 SceneTextStylizer (arXiv 2510.10910, 2025)**: training-free diffusion text style transfer; no runtime/limits read (U).
**2.11 MVFR (2024):** Bangla/Hindi/Spanish/Russian, 10 fonts each, 50k synthetic images per language, 400x200 white background (V). No CJK; shows the data-synthesis recipe (Pillow generator) we can reuse for the Keepframe synthetic test set.

## 4. What to avoid
- Open-ended "what font is this?" from a VLM or a DeepFont-style classifier: 24-31% or a closed commercial class list; both collapse on 3D, effects, blur (V).
- Neural scene-text editors (TextStyleBrush, MOSTEL, DiffSTE, TextCtrl, AnyText, TextDiffuser) as the primary editing path: GPU-bound, raster output (not editable text, not exportable to AE), colour inconsistency and metallic/gradient failures, weak Korean. Only as a hosted last resort for non-font text.
- Fill colour from a global background contrast percentile (current method): replace with local-plate matting (R2).
- Fitting font parameters on motion-blurred, wiping, or partially transparent frames; pick the sharpest, fully revealed frame.
- Copying numeric font weight across scripts without re-calibrating (Hangul looks heavier at equal weight).
